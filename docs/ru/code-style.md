# Кодстайл

Код должен быть предсказуемым и соответствовать соседнему модулю. ESLint и TypeScript задают обязательную базу; здесь перечислены правила ревью, которые не полностью выражаются инструментами.

## TypeScript

- Строгая типизация обязательна на границах процессов, файловой системы, сети, persistence и внешних провайдеров.
- Вместо `any` используйте `unknown` и явную валидацию.
- Существующие подавленные `any` — технический долг, а не пример. Новое исключение требует узкого комментария о несовместимой внешней границе.
- Cross-process interfaces живут в `shared/contracts/*` или `shared/types/*`; локальные типы процесса — рядом со своим доменом.
- Для state и outcomes используйте discriminated unions вместо сочетаний boolean с неоднозначным смыслом.
- Ошибка внешней библиотеки считается `unknown` и преобразуется в безопасное пользовательское или диагностическое сообщение.

`npm run lint` использует `--max-warnings 0`, поэтому warning считается падением.

## React и UI

- Компонент отвечает за отображение и взаимодействие. Provider, filesystem и orchestration логика выносится в service, context или feature hook.
- Не выполняйте тяжёлую работу во время render.
- Effect должен учитывать отмену или устаревший async-result, если его входы могут измениться.
- Используйте компоненты из `src/components/ui/` и semantic classes из `src/index.css`.
- Для меняющихся списков key строится по доменной идентичности, а не по индексу массива.
- У интерактивного элемента должны быть видимая подпись или accessible name и клавиатурное поведение.
- Пользовательская строка добавляется в оба locale-файла и читается через `t(...)`.

## Electron и IPC

Для новой или изменённой cross-process операции обновите всю цепочку:

1. payload/result type в `shared/contracts/*`;
2. `FriendLauncherApi`, если меняется preload surface;
3. preload bridge в `electron/preload/bridges/*` и exposure в `electron/preload.ts`;
4. валидацию входа main process;
5. регистрацию handler в `electron/ipc/*`;
6. domain service;
7. renderer wrapper в `src/services/ipc/*`;
8. focused tests;
9. обе карты контрактов при изменении канала.

Не добавляйте raw `ipcRenderer` в UI. Пути, URL, archive entries, identifiers и numeric limits из renderer нельзя использовать без main-process validation.

## Файлы и ответственность

- Группируйте код по домену, а не по абстрактным названиям вроде `helpers2` или `common-new`.
- IPC registration остаётся тонким; бизнес-логика живёт в services.
- Разбивайте файл, когда он владеет несколькими независимыми доменами или требует несвязанных test setup, а не по формальному числу строк.
- Используйте существующие общие policies для paths, URLs, archives, downloads и UI вместо локальных копий.
- Тесты лежат рядом с владельцем в `__tests__`; общие smoke и visual tests — в `tests/`.

## Ошибки и логи

- Пользовательское сообщение объясняет сбой и следующий шаг; технические детали остаются в логах.
- Нельзя логировать tokens, passwords, room codes или полный чувствительный account payload.
- Не публикуйте личные абсолютные пути в баг-репортах.
- Сохраняйте исходную ошибку как cause или диагностическую деталь там, где это позволяет boundary.

## Документация в code change

- При изменении поведения или mirrored contract обновите английский и русский документы.
- Роадмап меняется только при реальном изменении scope/status; история релизов живёт в `CHANGELOG.md` и GitHub Releases.
- Комментарий объясняет ограничение и причину, а не пересказывает следующую строку.

## Перед коммитом

Сначала запустите релевантные focused tests, затем:

```bash
npm run verify
git diff --check
```

Для UI, packaging и installation изменений нужны дополнительные проверки из [документа о тестировании](testing.md).
