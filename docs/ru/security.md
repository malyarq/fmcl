# Модель безопасности

Документ описывает границы доверия и действующие меры защиты Burrow. Он не означает, что в приложении нет уязвимостей. О подозрениях сообщайте по правилам [SECURITY.md](../../SECURITY.md), а не в публичной задаче.

## Границы доверия

Burrow обрабатывает несколько видов недоверенных данных:

- сообщения renderer-процесса, переходящие в основной процесс Electron;
- удалённые метаданные, изображения, загрузки, манифесты обновлений и серверы авторизации;
- импортируемые архивы сборок, миров, datapack, resource pack и shader pack;
- локальные пути, выбранные пользователем или полученные из импортированных метаданных;
- токены аккаунтов на локальном компьютере;
- LAN-узлы, UPnP-устройства, Burrow Link-узлы и локальный callback-трафик.

Renderer не считается доверенным только потому, что он поставляется вместе с приложением.

## Граница Electron

- Окна приложения работают в sandbox с context isolation и без Node integration.
- В production-пакетах отключены `ELECTRON_RUN_AS_NODE`, Node options и аргументы инспектора; включены шифрование cookie и проверка целостности ASAR; код приложения загружается только из `app.asar`.
- Переходы и открытие новых окон проверяются до передачи внешнего URL системе.
- CSP renderer-процесса запрещает inline-скрипты. Inline-стили пока разрешены: компоненты используют их для ограниченных значений темы.
- Операции renderer проходят через preload и список разрешённых IPC-каналов.
- Общие контракты описывают доступные renderer/main данные; секреты не должны попадать в DTO renderer-процесса.
- IPC-обработчики проверяют пути, URL, enum, размеры и идентификаторы до вызова сервисов.

Preload экспортирует один типизированный namespace `window.api`. Renderer не может выбрать произвольный канал из allowlist: каждая операция должна быть частью доменного контракта и bridge.

## Файлы, пути и архивы

- Перед изменением файлов пути разрешаются и ограничиваются ожидаемым корневым каталогом.
- Чтение архивов отклоняет абсолютные пути, выход из каталога, дубликаты, символические ссылки, зашифрованные записи, превышение числа или размера записей и несовпадение контрольных сумм.
- Загрузки ограничиваются при потоковом чтении и проверяют хеш, когда он получен из доверенных метаданных.
- Импортированные метаданные не дают права писать за пределами сборки или управляемого каталога данных.
- Разрушительные операции должны следовать явному действию пользователя и не переходить по недоверенным ссылкам.
- Управляемое JSON-состояние записывается через версионируемое атомарное хранилище с восстановлением из backup. Повреждённое или неподдерживаемое состояние сохраняется и вызывает явную ошибку, а не заменяется пустым значением.
- Save/export handler принимает только путь, однократно разрешённый нативным save dialog для того же renderer; другое окно и один абсолютный путь сами по себе не дают полномочий.
- Root mutation lock использует token-authenticated локальный Node socket как proof инкарнации процесса. Отсутствующий или отказавший уникальный socket означает dead для конкретного lease; таймауты и неоднозначные ошибки fail-closed. Смерть token разрешает удалить только его immutable ticket, но не общий endpoint процесса. Нельзя удалять canonical lock другой сборки во время живого обновления: перед upgrade, downgrade или смешиванием сборок с одним root остановите все процессы Burrow.

## Сетевые данные

- Удалённые адреса проходят проверку схемы и хоста. Для серверов аккаунтов обычно требуется HTTPS; loopback разрешён для локальных сценариев разработки.
- Запросы и архивы используют ограничения размера и времени там, где это поддерживает владеющий сервис.
- Разрешения браузера запрещены, если их явно не разрешила политика приложения.
- Публичные HTTPS-загрузки блокируют буквальные частные и зарезервированные адреса и проверяют DNS непосредственно при соединении. Все полученные адреса должны оставаться публичными, а перенаправления — использовать HTTPS; частные, локальные, зарезервированные адреса и переходы на HTTP отклоняются.

Нельзя расширять список разрешённых URL только ради одного провайдера. Нужны узкое правило, тесты и понятная обработка отказа.

## Аккаунты и секреты

- У offline-профиля нет удалённых учётных данных.
- Access/client token сторонних аккаунтов шифруются Electron `safeStorage` до сохранения и не возвращаются в объекты аккаунтов renderer-процесса.
- Если шифрование недоступно, сохранение стороннего аккаунта отключается вместо записи открытого текста. Linux-backend Electron `basic_text` явно считается небезопасным и недоступным.
- Логи, диагностика, снимки экрана, fixtures и отчёты об ошибках не должны содержать токены, пароли, материалы подписи и закрытые ключи провайдеров.

В Linux для стороннего аккаунта нужен поддерживаемый keyring рабочего окружения. Burrow не приравнивает такое хранение к аппаратной защите.

## Аналитика и обратная связь

- Аналитика требует согласия, по умолчанию выключена и использует встраиваемый при сборке project token PostHog, который разрешает только приём событий.
- Renderer отправляет события напрямую в документированный HTTPS capture endpoint; SDK autocapture, запись сессий, identify-вызовы и удалённая конфигурация аналитики не используются.
- Имена событий и свойства ограничены TypeScript allowlist. Сырые исключения, логи, пути, аккаунты, ники, адреса серверов и содержимое форм не входят в контракт.
- События используют `$process_person_profile: false`; при выключении удаляется локальный случайный идентификатор установки.
- Владелец релиза обязан отключить сбор IP в PostHog и использовать EU ingestion region. Подробности — в документе [Приватность](privacy.md).
- Отчёт для GitHub сначала показывается локально, редактируется и отправляется только самим пользователем.

## Релизы и обновления

- Публикация запускается только вручную. До publish job workflow заново проверяет точные тег и commit, checksums артефактов, platform smoke и schema-valid pre-push report.
- Локальный pre-push report — это доказательство для решения, а не security boundary или разрешение на публикацию. Для публикации в GitHub дополнительно нужно одобрение настроенного в репозитории protected Environment `release-publication`; код репозитория не может создать или гарантировать эту защиту.
- Release workflow собирает каждую платформу из исходного тега и публикует SHA-256.
- Windows-пакеты и macOS DMG пока не подписаны издателем. Ad-hoc подпись внутри локальной macOS-сборки нужна только для запуска Electron после настройки fuses и не подтверждает личность издателя. Контрольная сумма выявляет несовпадение, но также не устанавливает личность издателя. Поведение Gatekeeper и SmartScreen проверяется вручную на целевой платформе.
- Release candidate публикуется как prerelease и non-latest.
- Стабильные SemVer-теги и их файлы неизменяемы. Сломанный релиз исправляется новой patch-версией.
- Установка обновления должна быть явным поведением продукта и использовать метаданные из настроенного доверенного источника.

## Проверка изменений безопасности

Для изменений IPC, путей, архивов, загрузок, авторизации, навигации, обновления или локальных серверов:

1. Перечислите все недоверенные входы и привилегированные действия.
2. Проверяйте данные на границе main-процесса, а не только в интерфейсе.
3. Добавьте негативные тесты на выход из каталога, избыточный размер, неправильные URL и enum, отсутствие секретов — где это применимо.
4. Не записывайте чувствительные значения в лог и не возвращайте их renderer-процессу.
5. Зафиксируйте принятый остаточный риск в [известных проблемах](known-issues.md).
6. Запустите `npm run verify` и подходящую сборочную либо установочную проверку.
