# Выпуск релиза

Стабильные релизы используют неизменяемые SemVer-теги (`vMAJOR.MINOR.PATCH`) и GitHub Releases. Перемещаемый тег `latest` — только указатель на последний стабильный релиз.

## До создания тега

1. Начните с чистого и актуального `main`; его CI должен быть зелёным.
2. Просмотрите [известные проблемы](known-issues.md), обновите привязанные к версии роадмап и снимки контрактов, перенесите пользовательские изменения в [CHANGELOG.md](../../CHANGELOG.md).
3. После изменений интерфейса запустите визуальные проверки и просмотрите снимки.
4. После изменений установщика, обновления, Java или загрузчиков выполните подходящие ручные либо полные установочные проверки.
5. Выберите версию, для которой ещё никогда не создавался тег.

```bash
git switch main
git pull --ff-only origin main
nvm use
npm ci
npm run release -- <version> --dry-run
```

Пробный запуск выполняет `verify` и полную локальную сборку пакетов. Он не меняет отслеживаемые файлы, коммиты, теги и удалённый репозиторий, но обновляет игнорируемые результаты сборки.

## Создание и публикация

Скрипту нужен чистый рабочий каталог, активная ветка, корректная новая SemVer-версия и отсутствующий тег версии. Скрипт обновляет `package.json` и `package-lock.json`, создаёт один коммит и аннотированный тег.

```bash
npm run release -- <version> "chore: release v<version>" --push
```

Флаг `--push` отправляет текущую ветку и неизменяемый тег версии. Тег запускает `.github/workflows/release.yml`, который:

- проверяет версию, тесты, линтер, типы, документацию и IPC-контракты, зависимости и Linux-сборку;
- собирает неподписанные пакеты Windows, macOS и Linux на нативных runner;
- публикует единый GitHub Release только после успеха всех платформ;
- создаёт `SHA256SUMS.txt`, метаданные обновления и blockmap-файлы.

После успешного workflow переместите вспомогательный тег:

```bash
git tag -f latest 'v<version>^{}'
git push origin :refs/tags/latest
git push origin latest
```

Затем проверьте [страницу релиза](https://github.com/malyarq/fmcl/releases/latest), три установщика, контрольные суммы, описание релиза и цель тега `latest`.

## Ручной запуск workflow

Используйте `workflow_dispatch` только для повторной сборки **существующего неизменяемого тега версии** после инфраструктурного сбоя. Вводите полный тег, например `v0.8.0`. Не создавайте так релиз из случайного коммита `main`.

## Ошибка и откат

- До отправки тега исправьте проблему локально и повторите пробный запуск.
- После отправки не перемещайте, не перезаписывайте и не пересобирайте SemVer-тег из другого исходного кода.
- Если публикация упала до появления GitHub Release, исправьте workflow и повторите его для того же исходного тега.
- Если выпущенное поведение сломано, публикуйте новую patch-версию. Не заменяйте молча файлы существующей версии.
- Если контрольная сумма файла не совпала, считайте релиз скомпрометированным: уберите его из `latest`, предупредите пользователей, проведите разбор и выпустите новую patch-версию.

Подпись кода пока не настроена. Нельзя называть неподписанный файл подписанным или обходить создание контрольных сумм.
